Arbetsinstruktion för en ny Codex-flik
En ny Codex-flik ska behandlas som en ny arbetsyta utan antagande om att tidigare samtal, beslut eller godkännanden är kända. Den ska därför få en kort men komplett uppdragsbeskrivning med tydliga gränser.
Hur Codex ska arbeta
Grundsekvensen är:
READ
→ VERIFY
→ SNAPSHOT
→ CHANGE
→ TEST
→ HASH
→ REPORT
→ STOP
1. Inspektera före ändring
Codex ska först:
- bekräfta korrekt arbetskatalog;
- läsa den aktuella implementationen;
- identifiera vilka filer som faktiskt används;
- skilja aktuell implementation från historiska rapporter och gamla kopior;
- kontrollera befintliga kontrakt, identiteter och testmönster;
- kontrollera arbetsytans nuvarande ändringar så att användarens arbete inte skrivs över.
Historiska dokument är bakgrund, inte automatiskt aktuell auktoritet.
2. Arbeta från definierad auktoritet
För varje uppdrag måste det framgå vad som bestämmer resultatet, exempelvis:
- aktuell runtime;
- ett specifikt fryst artifact;
- en manifestfil;
- en viss CSV eller databas;
- en godkänd HTML-fil;
- en befintlig endpoint;
- en bestämd SHA-256-identitet.
Codex ska inte blanda flera möjliga källor eller välja den som verkar mest praktisk.
Om auktoriteten inte kan fastställas:
STOP
Ingen gissning, rekonstruktion eller “nästan motsvarande” källa.
3. Gör minsta sammanhängande ändring
Codex ska:
- ändra endast det som krävs;
- återanvända befintlig arkitektur;
- undvika parallella implementationer;
- undvika frivillig refaktorering;
- inte städa angränsande kod utan uttrycklig beställning;
- bevara befintliga ID:n, text, rangordning, hashes och kontrakt;
- lämna skyddade eller frysta artifacts byte-identiska.
En presentationsändring får inte bli en runtimeändring.
En deploymentuppgift får inte bli en vetenskaplig ombyggnad.
En inspektion får inte bli en implementation.
4. Bevara gränser och invariants
Varje order bör definiera sådant som inte får förändras:
retrieval
ranking
normalization
Evidence calculations
API contracts
database identities
frozen artifacts
existing COMPLETE runs
deployment configuration
unrelated frontend pages
Codex ska kontrollera dessa gränser efter arbetet, inte bara anta att de har bevarats.
5. Arbeta fail-closed
Om ett obligatoriskt villkor inte kan verifieras ska arbetet stoppas på ett tydligt sätt.
Exempel:
- fel artifact-hash;
- oklar endpoint;
- saknad registrering;
- motstridig population;
- okänd modellidentitet;
- schema som inte stämmer;
- ändringen skulle kräva arbete utanför tillåten scope.
Codex ska inte:
- använda fallback utan tillstånd;
- gissa en identitet;
- ersätta ett saknat artifact;
- rekonstruera frysta data;
- sänka valideringskrav;
- kalla en lokal testframgång för lyckad livedeployment.
6. Validera proportionerligt
Valideringen ska motsvara risken och uppdraget:
- fokuserade tester för den ändrade funktionen;
- relevanta regressionstester;
- kontroll av länkar och ankare för dokumentationsarbete;
- två deterministiska byggen när reproducerbarhet krävs;
- SHA-256 före/efter för skyddade filer;
- riktig HTTP-kontroll om ett live-endpointresultat påstås;
- lokalt test ska uttryckligen skiljas från liveverifiering.
Tester får inte ändras enbart för att få implementationen att passera.
7. Rapportera observerade resultat
Slutrapporten ska normalt innehålla:
- filer inspekterade;
- filer ändrade;
- exakt genomförd förändring;
- tester och kommandon som kördes;
- PASS/FAIL/STOP;
- relevanta SHA-256;
- skyddade identiteter som verifierats oförändrade;
- kvarvarande deploymentkrav;
- kända begränsningar.
Rapporten ska skilja mellan:
verifierat
observerat
antaget
inte verifierat
Inga vetenskapliga eller tekniska slutsatser får vara starkare än observationerna.


Hur en annan flik ska ge Codex instruktioner
En korrekt order ska vara begränsad och operativ. Den behöver inte vara lång, men den måste innehålla rätt saker.
Obligatoriska delar
Arbetsrot
Working root:
/absolut/sökväg/till/projektet
Använd faktiska sökvägar, inte platshållare.
Objektiv
En konkret slutpunkt:
Objective:
Uppdatera endast den publika Engineering-sidan så att den länkar till den befintliga Evidence API-dokumentationen.
Undvik vaga order som:
fixa dokumentationen
gör det bättre
städa projektet
Uppgiftstyp
Ange tydligt om uppdraget är:
INSPECTION ONLY
PLAN ONLY
IMPLEMENTATION
PRESENTATION ONLY
DEPLOYMENT PACKAGING
LIVE DEPLOYMENT
DESTRUCTIVE CLEANUP
En inspektionsorder ger inte rätt att ändra filer.
Auktoritet
Authority:
- site/dist/engineering.html
- aktuell Flask-route i Evidence_API/app.py
- specificerad manifestfil
Om en tidigare rapport bara är referens ska det också anges.
Tillåtna filer
Allowed to modify:
- site/dist/engineering.html
- site/dist/techs.html
Skyddade filer och system
Do not modify:
- runtime
- API routes
- databases
- frozen artifacts
- search behavior
- unrelated pages
Invariants
Beskriv vad som måste vara identiskt efter ändringen:
Endpoint paths unchanged
Response fields unchanged
Artifact SHA-256 unchanged
Retrieval ordering unchanged
Exakt önskat beteende
Skriv vad resultatet ska göra, inte hur Codex förväntas improvisera fram det.
Exempel:
engineering.html ska länka till techs.html.
technical_spec_fixed.html ska inte längre presenteras som aktiv dokumentation.
Ingen annan navigering ska ändras.
Acceptance criteria
Mätbara kontroller:
PASS if:
- länken från Engineering fungerar;
- samtliga lokala länkmål finns;
- inga skyddade filer har ändrats;
- HTML-valideringen passerar.
Stop conditions
STOP if:
- aktiv dokumentationsfil inte kan fastställas;
- ändringen kräver en API-routeändring;
- två aktuella källor motsäger varandra;
- en skyddad artifact måste skrivas om.
Leverans
Ange exakt vad svaret ska innehålla:
Return only:
- files changed
- tests run
- resulting hashes
- PASS/FAIL
Viktiga instruktioner för överlämning mellan flikar
En annan flik ska inte skriva:
Gör enligt det vi bestämde tidigare.
Den ska i stället bära med sig själva beslutet:
Fastställt beslut:
techs.html är den aktiva Evidence API-dokumentationen.
technical_spec_fixed.html är historiskt material och ska inte länkas från Engineering.
Den ska också ange om uppgiften bygger på:
- verifierade fakta;
- ett ägarbeslut;
- ett tidigare experiment;
- en aktuell hash;
- en ännu obekräftad hypotes.
En flik får inte presentera sin egen tidigare slutsats som fastslagen auktoritet utan att ange var den verifierades.
Deployment måste avgränsas särskilt
En deploymentorder måste säga om paketet är:
COMPLETE RUNTIME
eller:
DELTA PATCH
För en delta-patch måste instruktionen ange:
- nödvändig befintlig baseline;
- exakta filer som ersätts;
- målrot;
- backupsteg;
- archive-hash;
- reloadsteg;
- smoke tests efter deployment.
En patch får inte beskrivas som fristående om den kräver gårdagens runtime eller tidigare patchar.
Destruktiva handlingar kräver uttrycklig auktorisering
Om filer eller runs ska tas bort måste ordern identifiera:
- exakt målpopulation;
- varför den får tas bort;
- vad som måste bevaras;
- hur målidentiteten verifieras före radering.
Exempel:
Deletion explicitly authorized:
Endast experiment-ID A, B och C.

Preserve:
VALIDATION-001 och samtliga andra COMPLETE-runs.
“Städa” är inte tillräcklig raderingsauktoritet.

Kort mall att ge en ny Codex-flik
# TASK

Working root:
`/absolute/path`

Mode:
INSPECTION ONLY | IMPLEMENTATION | PRESENTATION ONLY | DEPLOYMENT PACKAGE

Objective:
<Ett konkret resultat>

Authority:
- <aktuell fil/artifact/endpoint>
- <identitet eller SHA om relevant>

Inspect first:
- <filer eller kontrakt som måste läsas>

Allowed to modify:
- <exakt fillista>

Do not modify:
- <skyddade filer/system>
- <runtime/data/artifacts som ska förbli oförändrade>

Required behavior:
1. <observerbart krav>
2. <observerbart krav>
3. <observerbart krav>

Invariants:
- <vad som måste vara identiskt>
- <vad som aldrig får räknas om>

Validation:
- <fokuserat test>
- <relevant regression>
- <hash/länk/identitetskontroll>

PASS if:
- <mätbara kriterier>

STOP if:
- <oklar auktoritet>
- <scope måste utökas>
- <skyddad identitet avviker>

Return only:
- files changed
- tests and results
- hashes
- PASS / FAIL / STOP

STOP after the requested result.
No adjacent cleanup or refactoring.
Kärnprincipen är:
Definiera auktoriteten. Begränsa ändringen. Bevara identiteterna. Validera det som faktiskt ändrades. Rapportera endast det som observerades. Stoppa när ordern är färdig.
